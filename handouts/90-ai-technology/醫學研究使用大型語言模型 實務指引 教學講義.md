## 1. 一句話總結 (Bottom Line)

> **這是 NIH／NLM（PubMed 的維護者）寫給臨床與研究人員的一份「LLM 落地作業指引」，不是綜述、也不是評論。**
>
> 核心主張很直白：**現在大多數人使用 LLM 的方式 —— 打開 ChatGPT 隨手問一問 (ad hoc prompting) —— 對醫療任務而言遠遠不夠。** 這種落差會同時造成**低度利用 (underutilization)** 與**誤用 (misapplication)**。
>
> 解方是一條有紀律的流水線：**任務形成 → 模型選擇 → 提示工程 → 微調 → 部署**，每一步都有明確的決策準則與 10 條最佳實務。其中對臨床端最關鍵的三條是：
> 1. **先收集約 100 個測試案例再開始**（沒有測試集就沒有品質可言）
> 2. **不要把可識別的病人資料放進非 HIPAA 合規的服務**
> 3. **不要用選擇題成績挑模型** —— MCQ 表現與真實臨床效用**不相關**

Drake 的定位：這篇不是「AI 有多厲害」的文章，而是**方法論工具書**。三個理由：

1. **來源權威且中立**。作者主體是 NLM（PubMed）、加上 Columbia、Yale、UIUC、UVA、Weill Cornell、FSU 與 NIH Clinical Center。**沒有模型廠商**。作者聲明無利益衝突。
2. **它把「怎麼做」寫成可執行步驟**，並附上公開的教學程式碼 repo，是少數能直接拿來設計院內流程或研究計畫的文件。
3. **它明確指出目前醫界最常見的兩個錯誤**：用 web app 處理病人資料、用考試分數挑模型。這兩點都在我們身邊天天發生。

> **給教學的一句話**：把這篇當成 LLM 版的 CONSORT／STROBE —— **它規範的不是結果，而是流程的可信度**。

## 4. 階段一：任務形成 (Task Formulation)

### 4.1 先問：這件事屬於 LLM 的哪一種能力？

作者把 LLM 的核心能力分成**五類**。第一步是辨識你的需求屬於哪一類 —— 因為**任務型態決定了資料格式與評估指標**。

| 能力 | 中文 | 醫療應用範例 | 任務實例的組成 | 評估方式 |
|------|------|-------------|---------------|---------|
| **Knowledge & reasoning** | 知識與推理 | 醫學問答、臨床決策支援、**病人與臨床試驗配對** | question (input) + explanation (reasoning output) + short answer (output) | 先比對短答案（如 yes/no），滿意後再深入分析解釋 |
| **Summarization** | 摘要 | ① 長病歷 → progress note / discharge summary；② 文獻 → 系統性回顧 | instruction + original text (input) + summary (output) | BLEU、ROUGE、BERTScore ⚠️ **但自動指標與人類判斷未必相關** |
| **Translation** | 轉譯 | 跨語言傳遞醫學知識、醫學教育、**醫病溝通**（也包括「換一種語氣寫給不同對象」） | instruction + source text + target text | 同摘要 |
| **Structurization** | 結構化 | 自由文字 → 結構化欄位；DRG 分類；抽取生醫概念與關係（如 variant-causing-disease） | instruction + source text + 結構化的概念與關係 (output) | **precision / recall / F1** |
| **Multimodality** | 多模態 | 放射報告生成、整合 EHR 病史 + 當次影像做決策 | 同推理，但輸入含多種模態 | 同推理 |

> 💡 **一個容易被忽略的洞見**：「Translation」不只是中英翻譯，**也包括寫作風格的轉換** —— 例如把一段技術性的病情說明改寫成病人聽得懂的話。這正是我們做衛教與醫病溝通最實際的用途。

> ⚠️ **反直覺的一點**：在**結構化**這類較簡單的任務上，**LLM 常常打不贏經過微調的 BERT 類模型**。LLM 的優勢在於**需要醫學知識與臨床推理**的任務，不是所有 NLP 任務。

### 4.2 最重要的一步：先建測試集

> **Best practice 1：收集約 100 個測試案例 (test instances)，每個都要有 input 與 output。**

作者依據數個 LLM 醫學評估研究的經驗，建議 **~100 個實例**。要求是**多樣 (diverse)**。

**為什麼這是整條流水線的地基？**

- 沒有測試集，你**無法比較兩個 prompt 誰比較好**
- 沒有測試集，你**無法知道換模型之後有沒有變差**
- 沒有測試集，你**無法在部署後偵測退化**

> 🔑 **這是本文對臨床端最重要、也最常被跳過的一條。** 大多數人的做法是「試幾個例子看起來不錯就上線」 —— 那不是評估，那是印象。

## 5. 階段二：模型選擇 (LLM Selection)

作者把選擇拆成**三個考量**，其中前兩項中的資料型態與 context window 是**硬限制 (hard constraints)**，其餘是**權衡 (trade-offs)**。

### 5.1 考量一：任務與資料 (Task and data)

#### (a) 隱私與法規 —— 這是臨床端的第一道關卡

> ⚠️ **作者的明確陳述**：透過 API 存取的專有模型（如 OpenAI 的 GPT-5）**通常不符合 HIPAA**，**因此不應用於病人資料**。
>
> **相對地**，某些雲端服務供應商 —— 文中點名 **Azure** 與 **Anthropic** —— **提供符合 HIPAA 的 LLM 存取**，可能可用於敏感資料。
>
> **或者**，使用**本地端模型**（如 Llama、Mistral）以獲得更強的隱私與安全控制。

**作者給的具體對照**：

| 做法 | 評價 |
|------|------|
| 醫院在**安全的本地伺服器**上，用**完全去識別化**的病歷微調模型，存取限於授權的內部人員 | ✅ 朝向合規 |
| 把**可識別的病歷**上傳到**公開的 LLM API** | ❌ 很可能違反法規，**尤其當該 API 可能拿使用者輸入去訓練模型時** |

> **實務準則**：使用任何服務前**先讀完供應商的使用者條款**；最佳做法是**只用明確聲明 HIPAA 合規的商用 API**，或在機構安全基礎設施內**部署本地模型**。

#### (b) 資料模態 (modality)

不同資料型態需要不同模型：

| 資料型態 | 需求 |
|---------|------|
| 放射科／病理 2D 或 3D 影像 | 需要**超越純文字**的模型（純文字模型如 o3-mini、Llama 3 不行） |
| 醫療對話（音訊） | 可先轉錄成文字，再用文字模型處理 |
| 基因體資料（DNA 序列、RNA 表現） | 需要 omics 資料判讀的知識 |
| 時序資料（如生命徵象監測） | 需要能分析結構化 EHR 中長時間模式的模型 |

> ⚠️ 作者明確指出：基因體與時序資料**雖然可以表示成純文字**，但**一般 LLM 能否在不經額外訓練的情況下有效處理這類輸入，仍不清楚**。

> **Best practice 3：確認任務必需的資料模態，並選擇支援該模態的 LLM。**

#### (c) Context window（上下文長度）

必須先了解自己資料集的**長度分布**，再選擇 context window 足夠的模型。

**作者提供的實用換算**：

```text
1 個 token ≈ 0.8 個英文字
（因為文字常被切成 subword 與單一字元）

一篇 PubMed 文章的 title + abstract
  ≈ 250 字 ≈ 300–400 tokens
```

**換算成「一次能塞幾篇摘要」**：

| 模型 | Context window | 約可容納摘要數 |
|------|---------------|--------------|
| Llama 3.0 | 8,000 tokens | ~20 篇 |
| Claude 4.5 Opus | 200k tokens | ~800 篇 |
| GPT-5 | 400k tokens | ~1,600 篇 |
| Gemini 3.0 | 1M tokens | ~2,500 篇 |

> ⚠️ **但長 context 不是萬靈丹**：作者特別點名 **lost-in-the-middle** 現象 —— **模型會用不到放在提示中間的資訊** —— 這個問題**在長 context 模型上同樣存在**。
>
> **實務啟示**：重要的東西**放頭尾**，不要埋在中間。

### 5.2 考量二：效能要求 (Performance requirements)

一般而言**模型越大能力越強**，但需要更多資源；小模型較省、較永續，但表現通常較弱。

**兩種評估路線**：

| | 自動評估 (automatic) | 臨床評估 (clinical) |
|---|---|---|
| 方法 | 標準化 benchmark：MedQA-USMLE、PubMedQA、MedMCQA 等選擇題 | 真實醫療情境測試，如**隨機對照試驗** |
| 優點 | 可規模化、可作為起點 | **黃金標準**，與病人照護相關 |
| 缺點 | ⚠️ **分數高不等於臨床效用好** | 耗費大量人力，且常常拿不到 |

> ⚠️ **本文最重要的警告之一**：
> **在多選題 benchmark 上分數更高，不必然轉換為更好的臨床效用。** 因為真實應用中**根本沒有選項可選**；且多項研究顯示 **MCQ 表現與真實任務效用不相關**。
>
> 較有前景的方向是**開放式評估**：以評分表為基礎的 **HealthBench**，與以偏好為基礎的 **Chatbot Arena**。

> **Best practice 4：優先依據「臨床評估」的結果選模型；若拿不到臨床評估，才用自動評估來篩選候選模型，再進一步做臨床評估。**

### 5.3 考量三：存取介面 (Model interface)

| 介面 | 優點 | 缺點 | 作者建議 |
|------|------|------|---------|
| **Web 應用**（如 ChatGPT） | 便宜、易用 | ❌ 無法彈性控制模型行為、無法大規模評估；**多數不具明確 HIPAA 合規**；**通常無法設定 temperature** | ⚠️ **不建議在開發階段使用** |
| **模型 API** | 比自架容易；**部分提供 HIPAA 合規服務**；可控制參數 | 對專有模型的客製化受限 | 多數情境的實務選擇 |
| **本地部署** | **最大的控制權與隱私**；可取得特定參數與**下一個 token 的原始機率分布** | 硬體與技術門檻高 | 敏感資料／需深度客製時 |

**總結權衡**：

> 尖端專有 LLM 在一般任務上表現較好，但**在客製化、隱私與安全上使用者掌控較少**；開源 LLM 允許更大的客製化與安全性，但**在開發與部署兩端都需要更高的硬體與技術能力**。

## 6. 階段三：提示工程 (Prompt Engineering)

**定義**：設計與最佳化提示，以有效引導 LLM 產生準確、連貫回應的過程。

**核心觀念**：提示工程**不修改模型參數**，就能引導出多樣的行為。任務越複雜，通常需要越精緻的提示。

**方法**：可人工迭代設計，也可用 **DSPy**、**TextGrad** 這類框架，讓 LLM 依效能回饋自動調整與優化提示。

> 🔑 **作者給的方法論主軸**：
> **先分析錯誤 (error analysis)，再依錯誤型態選技術。**
> 例：如果錯誤肇因於**缺乏醫學知識** → 用 **RAG** 把相關資訊餵給模型。

### 6.1 四項核心技術

#### ① FSL — Few-Shot Learning（少樣本學習）

在提示中放入**少數幾個範例（shots）**來界定任務。每個示範都要**同時包含輸入與期望的輸出**。

- 零個、一個、多個（如五個）範例，分別稱 zero-shot、one-shot、few-shot
- 範例應**盡可能有代表性且多樣**；分類任務應**展示所有可能的標籤**（例如各種疾病亞型）
- 進階做法：**依待預測實例的語意相似度，動態生成範例**

> **Best practice 5：從 zero-shot 開始，再逐步增加範例來提升效能或處理邊緣案例。**

#### ② CoT — Chain-of-Thought Prompting（思維鏈提示）

設計提示引導模型走過**逐步推理過程**。

- 最簡單的做法：在輸入末尾加上 **"Let's think step-by-step"**
- 在複雜醫療決策任務中特別有用：**推理過程的說明可提升效能，也幫助臨床醫師理解與驗證 AI 給的建議**

> **Best practice 6：把 CoT 當成預設值** —— 因為它同時提升**可解釋性**與（可能的）效能。

> 💡 **對臨床的意義**：一個只給答案的 AI 無法被查核；一個給出推理的 AI 才可能被醫師**驗證與否決**。這是安全性議題，不只是效能議題。

#### ③ RAG — Retrieval-Augmented Generation（檢索增強生成）

由**搜尋引擎檢索相關文件**（如科學文獻），放進提示中，讓模型能處理知識密集的任務。

**RAG 解決兩個醫療上特別危險的問題**：

| 問題 | 說明 |
|------|------|
| **幻覺 (hallucination)** | 生成不正確的內容**或不存在的參考文獻** |
| **知識過期** | LLM 參數中編碼的知識停留在訓練時點 |

> **兩者在醫療應用中都特別令人憂心，因為會影響病人安全與臨床決策。**

**作者建議的 RAG 語料**：

> 使用**高品質、領域專屬的語料** —— **系統性回顧、醫學教科書、臨床指引**。
> 常用資源：**PubMed**（超過 3,900 萬篇免費摘要）、**PubMed Central**（超過 700 萬篇開放取用全文，可供文字與資料探勘）。

> **Best practice 7：善用 RAG 與工具呼叫。**

#### ④ Tool learning（工具使用／function calling）

某些醫療任務需要**領域專屬工具** —— 例如資料庫查詢工具或**醫學計算機**。若這些工具實作為 API，LLM 可透過 **function calling** 機制使用它們。

> **例**：在臨床試驗配對任務中，可提供 LLM「讀取原始電子病歷」的工具，以擷取病人摘要中可能遺漏的細節。

> 💡 **臨床啟示**：與其要求 LLM「心算」CHA₂DS₂-VASc 或 eGFR，不如**給它一個計算器工具**。演算法該交給演算法。

### 6.2 Temperature（溫度）設定

控制生成回應的**隨機程度**：低溫 → 輸出較一致；高溫 → 回應較有創意。

> **Best practice 8：從 temperature = 0 開始**，取得**確定性 (deterministic) 的結果以確保可重現性 (reproducibility)**；只有在需要多樣回應（例如做 ensembling）時，才考慮調高。

⚠️ Temperature 通常**可透過 API 或本地端參數設定，但 web app 通常不行** —— 這是不建議用 web app 做開發的另一個具體理由。

### 6.3 輸出格式

> **Best practice 8（同條）：指示 LLM 產生結構化輸出，例如 JSON 字典**，讓結果容易被自動解析成不同的答案區段。

主要考量是**自動解析回應的難易度**。

### 6.4 多模態與其他細節

- 單細胞 RNA 定序資料可轉成含**基因標記與表現量**的文字提示
- 生物感測器訊號可轉成文字，用以生成個人健康洞察與運動建議
- 實務上也可探索較經驗性的微調整：聚焦的範例、**上下文擺放與包裝的位置**、多樣本範例的組織方式 —— 特別是在早期迭代開發階段

## 7. 階段四：微調 (Fine-Tuning)

### 7.1 什麼時候才需要微調？

> **只有三種情況才考慮 (Best practice 9)：**
> 1. **提示工程技術（如 FSL、RAG）已無法充分改善結果**
> 2. **有大規模、現成的高品質訓練資料**
> 3. **可用的提示長到成本上不可行**

> 🔑 **反過來說：如果這三條都不成立，就不要微調。** 這是本文對想「訓練自己的醫療 AI」的團隊最務實的提醒。

### 7.2 全量微調 vs PEFT

| | Full fine-tuning | PEFT（如 LoRA） |
|---|---|---|
| 更新範圍 | **全部參數** | **遠少於全模型的參數** |
| 適合的資料 | **較大、較多樣**的資料 | **較小、較專一**的資料（**避免過擬合 overfitting**） |
| 硬體需求 | 高 | **大幅降低** |
| 效能 | — | **常與全量微調相當，在低資料量情境甚至更好** |

**作者給的具體案例**：使用 **quantized LoRA (QLoRA)** 微調 LLM 做臨床文本摘要，**僅用數千筆訓練實例與一張 NVIDIA Quadro RTX 8000 GPU** 即達成有效結果。

### 7.3 執行方式與必要紀律

- 可在本地伺服器執行，或透過 LLM／雲端廠商提供的**網頁圖形介面** —— 後者技術門檻較低，**但實作細節可能不完全透明**
- ⚠️ **與提示工程一樣，微調後的模型必須在「獨立的測試集」上評估**，以驗證訓練確實帶來效能提升

## 8. 階段五：部署 (Deployment)

### 8.1 法規遵循 (Regulatory compliance)

- 須遵守 **HIPAA** 與 **GDPR** 等隱私標準
- 使用專有 LLM 時，**必須確認平台符合 HIPAA**
- 作者具體點名：**OpenAI API 目前不符合 HIPAA**；**Azure 提供符合 HIPAA 的 OpenAI 模型存取**；**Anthropic 為其 Claude 模型提供 HIPAA 認證的 API 託管**
- ⚠️ **LLM 這類 AI 演算法有可能被視為醫療器材而受管制** —— 尤其在**臨床場域使用或用於決策支援**時，會需要符合 **FDA** 或其他主管機關對醫材軟體的規範

> **Best practice 10：謹慎選擇符合法規與臨床標準的協定，並持續監測。**

### 8.2 系統穩健性與公平性 (System robustness)

> ⚠️ **作者的明確警告**：**即使是最成功的專有模型也可能展現種族偏誤。**
> 研究顯示，當提供**僅在種族上不同、其餘完全相同的病人描述**時，**LLM 可能對治療、費用或預後給出不同的預測**。
> 這種差異**在正式運作時會造成醫療不平等 (healthcare disparities)**。

**因此**：部署前**必須評估模型公平性**。若無法檢視資料或演算法（許多專有模型即是如此），仍可**使用既有的 benchmark 資料集評估**，以了解模型是否存在偏誤、以及偏誤的程度。

### 8.3 成本 (Costs)

**專有模型**：按次計費。作者給的實例（截至 2025 年 12 月）—

```text
Google Gemini 3.0
  input  : US$2  / 1M tokens（提示 < 200k tokens 時）
  output : US$12 / 1M tokens

實例：處理 1,000 份典型的 MIMIC-III 出院病摘
      ≈ 400 萬 tokens
      ≈ US$8（僅計入提示 token；輸出另計）
```

**開源模型**：前期硬體採購（GPU）與持續維運成本。

| 模型規模 | 硬體需求 |
|---------|---------|
| 較小的 instruction-tuned 模型（如 **7–8B** 參數） | 常可用**單張高記憶體 GPU**（如 NVIDIA A100 40GB）有效服務；**若能容忍較高延遲，甚至可用 CPU** |
| 較大模型（如 **70B** 參數） | 通常需要**多 GPU 配置或 tensor-parallel serving** |

**節省技巧**：較新的模型（如 Qwen3）提供 **FP8（8-bit 浮點）變體** —— 參數以 8-bit 浮點儲存與運算，而非標準的 16/32-bit，**GPU 記憶體用量約減半**（相較 FP16）。

**權衡總結**：

> 本地執行**前期成本較高，但可由較低的持續成本抵銷**，並額外獲得「**可用受保護資料微調**」與「**對系統回應性與更新的掌控**」等好處。
> ⚠️ 但要考慮**本地高需求時段的延遲增加與吞吐量下降** —— 本地設備的速度與回應時間**未必能比得上大公司託管的 LLM**。

### 8.4 上線後 (Post-deployment)

**持續監測是必要的 (Best practice 10)。** 作者強調四件事：

1. **定位**：必須確保 LLM 的輸出被**負責任地當作輔助工具使用，而非取代醫療專業人員的判斷**。
2. **訓練**：有效的訓練計畫至關重要，協助醫療人員理解**如何解讀與運用這些輸出、並管理潛在風險**。
3. **社群參與**：成功整合需要與**病人及在地社群主動合作** —— 透過**社群諮詢委員會 (community advisory boards)** 與**病人小組 (patient panels)** 收集有意義的回饋，讓應用貼近真實世界的病人多樣性。
4. **模型生命週期管理**：⚠️ **模型的淘汰或替換，可能需要重新實作提示、重新驗證效能、重新認證安全性與合規性。**

> 🔑 **第 4 點最容易被忽略**：你依賴的模型版本**會被下架**。所以要問的不是「這個 prompt 現在好不好用」，而是「**換模型的那一天，我們要花多久重跑驗證？**」—— 這就是為什麼 **Best practice 1（先建 100 個測試案例）** 是整條流水線的地基。

## 10. 評估：為什麼「考試考很高」不等於「好用」

這一節值得單獨拉出來，因為它直接對應醫學教育界最常見的誤解。

```text
常見的推論（錯誤）
  「這個模型 USMLE 考 90 分 → 它可以看門診」

作者的反駁
  ① 真實臨床「沒有選項可選」
     MCQ 提供 5 個選項，其中必有 1 個正確
     真實情境是開放式的，且可能沒有正確答案
  ② 多項研究顯示 MCQ 表現與真實任務效用「不相關」

正確的做法
  自動評估 → 只用來「篩選」候選模型（可規模化、便宜）
       ↓
  臨床評估 → 才是黃金標準（如 RCT），但耗費人力
       ↓
  開放式評估是有前景的中間路線
     · HealthBench（以評分表 rubric 為基礎）
     · Chatbot Arena（以偏好 preference 為基礎）
```

> 💡 **對醫學教育的延伸思考**：這個論證的結構，和我們討論「**筆試成績能不能預測臨床表現**」是同一個問題。作者的立場等同於 Miller 金字塔 —— **knows ≠ knows how ≠ shows how ≠ does**。用 MCQ 挑 LLM，就像用筆試挑住院醫師。

## 12. 限制與該注意的地方

**這篇文章本身的性質與限制**：

1. **這是 Tutorial，不是系統性回顧，也不是實證指引。** 它提供的是**專家共識性質的操作框架**，其建議（如「~100 個測試實例」）是**基於數個評估研究的經驗法則**，不是經過檢定的閾值。
2. **技術細節會快速過期。** 文中的模型名稱、context window 大小、價格（明確標註「as of December 2025」）都會變動。**框架會存活，數字不會。**
3. **合規陳述有時效與地域性。** 「某某服務是否 HIPAA 合規」會隨供應商政策改變；且 **HIPAA 是美國法規** —— 台灣適用的是**個人資料保護法**與各院 IRB／資安規範，**不能直接套用**。
4. **沒有提供醫療機構層級的治理範本**（如採購、稽核、事故通報流程），這些仍需各院自行建立。
5. **公平性章節指出問題，但未給出可操作的檢測流程**；只建議「使用既有 benchmark 評估」。

> ⚠️ **給台灣讀者的具體提醒**：文中所有 HIPAA 相關建議，在我們的情境下應轉譯為「**符合個資法、通過院內資安與 IRB 審查的路徑**」。**不要因為某服務標示 HIPAA 合規，就認定在台灣可直接用於病人資料。**

## 13. Take Home

> **Pearl 1**：這是 **NIH／NLM（PubMed 的維護者）** 寫的操作指引，作者群**不含模型廠商**、聲明無利益衝突。定位是**方法論工具書**，不是綜述。

> **Pearl 2**：框架五階段 —— **任務形成 → 模型選擇 → 提示工程 → 微調 → 部署**。注意**提示工程排在微調之前**：多數醫療任務**不需要微調**。

> **Pearl 3（最常被跳過）**：**先收集約 100 個測試實例再開始。** 沒有測試集就無法比較 prompt、無法察覺換模型後的退化、無法在上線後偵測劣化。

> **Pearl 4（臨床紅線）**：**透過 API 的專有模型通常不符合 HIPAA，不應用於病人資料。** Azure 與 Anthropic 提供 HIPAA 合規存取；或改用本地模型。**把可識別病歷丟進公開 API 很可能違法**，尤其當該 API 會用輸入去訓練模型時。

> **Pearl 5（挑模型的紅線）**：**不要用 MCQ 成績挑模型。** 真實情境沒有選項可選；多項研究顯示 MCQ 表現**與真實任務效用不相關**。自動評估只能用來**篩選**，臨床評估才是黃金標準。

> **Pearl 6（四件武器）**：**FSL**（從 zero-shot 開始加）、**CoT**（設為預設，因為可被醫師驗證）、**RAG**（對抗幻覺與知識過期，用系統性回顧／教科書／指引當語料）、**Tool learning**（計算交給計算器）。**temperature = 0** 以求可重現。**輸出 JSON** 以便解析。

> **Pearl 7**：**Web app 不適合開發** —— 無法控制參數（連 temperature 都設不了）、無法規模化評估、多數不具明確 HIPAA 合規。

> **Pearl 8**：**LLM 不是所有 NLP 任務的答案。** 在**結構化**這類簡單任務上，**微調過的 BERT 常常更好**。LLM 的主場是**需要醫學知識與臨床推理**的任務。

> **Pearl 9（公平性）**：**僅改變種族、其餘完全相同的病人描述，LLM 可能給出不同的治療、費用或預後預測。** 部署前必須評估公平性。

> **Pearl 10（生命週期）**：**你依賴的模型會被下架。** 淘汰或替換需要**重新實作提示、重新驗證效能、重新認證合規** —— 這正是 Pearl 3 的測試集在真正發揮價值的時刻。

> **Pearl 11（台灣在地化）**：所有 HIPAA 建議須轉譯為**個資法 + 院內資安 + IRB** 的路徑。**HIPAA 合規 ≠ 台灣可用。**
